A customer will sometimes text a card number or read one out to voicemail. The engine never keeps it. Every text in or out, every voicemail transcript, every call transcript and summary is masked on the way in, so what the app shows, what the push notification carries and what Zoho receives is already clean.

## What a masked message looks like

| Written by the customer | Kept by the engine |
|---|---|
| my visa card number is 4242 4242 4242 4242 | my visa card number is `[CARD ****4242]` |
| expiry 12/28 | expiry `[EXP]` |
| cvv 123 | cvv `[CVV]` |

The last four digits are kept so the office can still say "the card ending 4242". A number is treated as a card only when it passes the checks a real card passes, so a phone number or an invoice number is left alone.

## The hourly scan

Every hour, at 45 minutes past, the engine re-reads every stored text, transcript and summary. If a card number is found, the owner gets an email titled "[ops] a card number is stored in …" naming the row, with the fix to run, once per row until it is cleaned. The card itself is never in the email.

On 4 September 2026 the scan found 0 rows across all seven places it looks. Later that day a card was planted in a probe transcript line on purpose, and the email arrived once; see below.

## What was observed

Tested 4 September 2026 (<Linear issue="COM-108" />) with a made-up caller named "Probe simulator" and the test card 4242 4242 4242 4242:

- An inbound text carrying the card, an expiry and a security code was stored masked, as in the table above, and the "new text" push to the three agents carried the masked wording.
- A voicemail transcript reading the same card out loud was stored masked.
- The scan run straight afterwards found nothing to report.

Later the same day, at 5:46 pm Toronto time:

- An outbound text carrying the same card, an expiry and a security code was queued from the outbox to the owner's verified number. The stored copy read `my visa is [CARD ****4242], expiry [EXP], cvv [CVV]`, and Twilio's own record of the message, read back by its id, carried the same masked wording (with Twilio's trial-account prefix in front). The text left in 1.7 seconds and was delivered in 4.9 seconds.
- A raw card was then written into one probe transcript line with the masking switched off for that single write, which is the only way to get one past it. The scan, woken by hand, emailed the owner "[ops] a card number is stored in" the transcript-lines column 2.6 seconds after the wake, once, with the row id and the fix to run. The card itself was not in the email. The planted line was deleted and the scan found 0 rows again.

Not tested: a card typed into an outbound text from the app screen itself. The text above was queued straight into the outbox, which is the same write the app makes.

## When a text is deleted

The Messages list shows, for each conversation, the newest text and when it arrived. Until 5 September 2026 that line was written only when a text arrived, never when one was removed. So when the probe's clean-up deleted the masked card text above, the list kept saying "3:10 PM, my visa card number is [CARD ****4242]…" and showed the conversation as unread, while opening it showed only the two morning texts. Nothing was lost to the masking: the text had been kept, masked, and the push had gone out; the list was simply describing a text that had since been deleted (<Linear issue="COM-210" />).

Now, when a text is deleted, the conversation's line is rebuilt from the texts that remain: the newest remaining text becomes the preview, its time becomes the conversation's time, and the conversation is unread only if an incoming text is still there. Delete the last text and the line goes blank. The list and the thread can no longer disagree.

Deleting a text is not something the app offers; it happens when a probe is cleaned up or when a developer removes a row by hand.
